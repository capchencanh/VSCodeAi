# Ghi chú kiến thức — làm việc local (không qua MCP)

Mục đích: lưu kiến thức rút ra khi làm việc không gọi tool MCP SAP (đọc/sửa file trong `Code/`, review code user dán vào, tư vấn thiết kế) để lần sau không lặp lại sai lầm. Khi nào đọc/ghi file này: xem mục "Ghi chú kiến thức tích lũy" trong [CLAUDE.md](CLAUDE.md).

**Phạm vi:** kiến thức ngôn ngữ ABAP/CDS, ràng buộc nền tảng, thiết kế, logic nghiệp vụ và object tái sử dụng được của dự án. Hành vi tool MCP (tool nào lỗi/chạy tốt) thuộc [`.claude/skills/sap-mcp-gui/reference/_ghichu_mcp_gui.md`](.claude/skills/sap-mcp-gui/reference/_ghichu_mcp_gui.md) / [`.claude/skills/sap-mcp-cloud/reference/_ghichu_mcp_cloud.md`](.claude/skills/sap-mcp-cloud/reference/_ghichu_mcp_cloud.md).

**Tham khảo chéo khi làm Public Cloud:** [`.claude/skills/sap-mcp-cloud/reference/_ghichu_mcp_cloud.md`](.claude/skills/sap-mcp-cloud/reference/_ghichu_mcp_cloud.md) đã có nhiều rule cú pháp CDS/ABAP Cloud xác nhận qua SyntaxCheck/activate, áp dụng được cả khi làm local — tra các mục "Giới hạn cú pháp CDS", "Kinh nghiệm thiết kế CDS", "Giới hạn cú pháp ABAP OO", "Quy trình tạo CDS UNION view" trước khi viết CDS/class.

**Mẫu 1 mục ghi chú:**

```
- **<Quy tắc rút ra, 1 câu>** — <object/chương trình, dd.mm.yyyy>. Nguồn xác nhận: <user dán lỗi activate / user xác nhận kết quả chạy / tài liệu SAP>. <Cách xử lý đúng, kèm code ngắn nếu cần>.
```

**Trước khi thêm 1 mục (đúc kết 24/09/2026):**
1. Đã có mục nào nói cùng ý chưa? Có thì gộp/bổ sung, không tạo mục mới lặp ý cũ.
2. `<object/chương trình>` chỉ tồn tại ở 1 dự án cụ thể → ghi rõ "riêng dự án X", không để đọc như thể dùng chung mọi nơi.
3. Nếu là kiến thức ngôn ngữ ABAP/CDS/authorization dùng được nhiều dự án (không riêng 1 object/dự án) → thêm bản rút gọn vào `SKILL.md` liên quan, kèm link ngược lại mục này. Chi tiết: skill `skill-authoring`.
4. Mục dài (>~80 từ): mở đầu bằng 1 câu kết luận in đậm rồi mới tới chi tiết/bằng chứng.
5. Đánh dấu rõ `**[CONFIRMED]**` (đã verify qua case thật) hay `**[NGHI NGỜ/TODO]**` (suy đoán, chưa test) — không lẫn 2 loại cùng giọng chắc chắn như nhau.
6. Tái xác nhận đúng bài học đã có → chỉ dẫn chiếu ngược ("xem mục X, tái xác nhận qua case Y"), không viết lại toàn bộ diễn giải cũ.
7. Không dán nguyên văn lỗi dài (stack trace/JSON/XML) — chỉ giữ message chính, phần dài cần lưu thì để trong file `.sql`/log riêng.
8. 1 bug/vấn đề bị test lại nhiều lần → gộp thành 1 mục có mốc thời gian con, không rải nhiều đoạn rời rạc.
9. File vượt ~300 dòng hoặc 1 chủ đề hẹp phình to → tách sang file `_ghichu_<chủ đề>.md` riêng, để lại 1 dòng tóm tắt + link.
10. Mục đã hết hiệu lực (đã fix/không còn đúng) → đánh dấu `~~gạch ngang~~`/"[OUTDATED]" kèm lý do, không xoá âm thầm.

### Chuẩn tài liệu TS (Technical Specification) của CITEK — đã đóng gói thành skill `sap-ts-document`

- **Khung TS chuẩn của công ty cố định 9 mục, không đổi thứ tự/cách đánh số; mục không áp dụng ghi `N/A` chứ không xoá** — 22.09.2026. Nguồn xác nhận: đọc trực tiếp file phát hành thật `CodeABAP/Document/GGFs_TS_Chucnang&TichhopAPI_trahangbannoibo_MM13_V1.0.docx` (GGFs – MM.13, V1.0, 18/03/2024). Thứ tự: 1.1 Mô tả chung → 1.2 Yêu cầu nghiệp vụ chi tiết (chỉ trỏ tên file FS) → 2.1 Cấu hình hệ thống → 2.2 Object List → 2.3 Flow Diagram → 2.4 Enhancement (file mẫu dùng mục này cho **cả object DDIC**: message class, structure, transparent table) → 2.5 Job Scheduling → 2.6 Error Handling → 2.7 Function Module → 2.8 Parameter/Selection-screen → 2.9 Display output → 2.10 Logic lấy data. Bảng cột cố định: Object List = `No. | Object Name | Object Type | Description | File`; Selection-screen = `Description | Type | Field name | SAP table | Default | Required`; Display output = `Description | SAP field | Logic`. Chi tiết cách viết + template điền sẵn: `.claude/skills/sap-ts-document/`.
- **Prefix object On-Premise dùng trong tài liệu CITEK** — cùng nguồn, 22.09.2026: Program `Z<PH>_PG_*`, Include `Z<PH>_IN_*_TOP`/`_F01`, Transaction `Z<PH><nn>` (VD `ZIT01`), Transparent table `ZTB_*_HD`/`_DT` (cặp header–item), Structure `Z<PH>_ST_*` hoặc `ZST_*` (dùng chung), Message class `ZMC_*`, Function module `ZFM_*`, Enhancement implementation `ZEI_<Tcode>_<mô tả>`, Proxy class outbound `ZCO_SI_OUT_*`, Implementing class inbound `ZCL_SI_IN_*`, Proxy interface `ZII_SI_IN_*`, Method proxy `SI_IN_*`. Field ALV: icon đặt `<FIELD>_ICON`, giá trị cập nhật đặt `<FIELD>_U`. Đây là quan sát từ 1 dự án (GGFs) → đối chiếu Z-object đã có của dự án đang làm trước khi áp dụng.
- **Máy dev không có `pandoc`/`python` nhưng CÓ Node.js v24 + Microsoft Word → vẫn convert Markdown → `.docx` tự động được, đã chạy thật** — 22.09.2026 (*sửa kết luận ghi buổi sáng cùng ngày là "không có đường convert tự động" — sai*).   - **Luôn validate `[xml]` trước khi đóng gói** — đây là bước chặn được lỗi "Word cần repair file", rẻ hơn nhiều so với debug sau khi Word từ chối mở.
  - **Cập nhật field số trang trong footer phải gọi riêng header/footer của section** (cập nhật 27.09.2026). Chỉ chạy `$d.StoryRanges` (kể cả đi hết `NextStoryRange`) thì footer vẫn kẹt giá trị `NUMPAGES` cũ của template — case thật: tài liệu 23 trang mà footer hiện "Trang 1/8". ### Quy ước nội dung TS gửi khách hàng (cập nhật 22.09.2026)

- **TS là tài liệu chính thức gửi khách → KHÔNG có phụ lục, KHÔNG có mục nhận xét/rủi ro/đề xuất sửa code, KHÔNG lộ thông tin nội bộ** (tên MCP server, hostname, "tài liệu lập ngược từ source", chuyện tool đọc được hay không). Nguồn xác nhận: user chốt trực tiếp 22.09.2026. Chỉ mô tả code đang làm gì; hành vi thật vẫn ghi kể cả khi là hệ quả của lỗi (VD "câu SELECT nạp GT_MARA đang được comment nên cột hiển thị rỗng" — hợp lệ; "đây là bug cần sửa" — không hợp lệ). Phát hiện lỗi/hiệu năng ghi vào file ghi chú này + báo user trong chat.
- **TEMPLATE HÌNH THỨC MỚI NHẤT cho TS = `CodeABAP/Document/BIDIPHAR_BP_SD_V2.0.docx`** (user chốt 27.09.2026, thay template GGFs cho phần font/màu/bìa/header/footer; GGFs vẫn là chuẩn nội dung 9 mục). Đọc trực tiếp `document.xml`/`styles.xml`/`header1.xml`/`footer1.xml`: A4 **dọc** (`11906×16838`, lề trái 1440 phải 1134 → vùng in **9332 twips**); `Normal` = Myriad Pro 11pt màu `333333` nhưng mọi run thân bài/ô bảng tô trực tiếp `00586F`; tiêu đề bìa đậm `sz 40` + phụ đề nghiêng `sz 32` (`Phân hệ ... – SAP S/4HANA`) + đoạn kẻ ngắn viền dưới `sz 24` màu `A2D45E` thụt `3969` 2 bên; viền bảng `BFBFBF sz 4`; lề ô `60/100`; ô bảng KHÔNG khai spacing (kế thừa `after=200`).
